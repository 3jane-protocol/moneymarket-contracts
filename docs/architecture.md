# Architecture

## Overview

This repository extends Morpho Blue with 3Jane credit primitives and USD3/sUSD3 strategy logic.

## Contract Structure

- `src/Morpho.sol`: base market operations and accounting.
- `src/MorphoCredit.sol`: credit-line and borrower-premium extensions using hook overrides.
- `src/libraries/`: core libraries (`MathLib`, `SharesMathLib`, `UtilsLib`, and related helpers).
- `src/libraries/periphery/`: helper libraries for integrators.
- `src/mocks/`: test-only mock contracts.

## Core Data and Accounting Model

- Market identity is derived from `MarketParams` hashed into `Id`.
- Position and market state are share-based, not balance-based.
- Interest accrual updates borrow/supply state before operations.
- Premium accrual is borrower-specific and integrated through hook entry points.

## 3Jane Credit Extensions

- Unsecured lending path via credit-line controls.
- Per-borrower premium model layered on top of base IRM rate.
- Settlement paths include write-off handling and JANE markdown/redistribution integration.

## Jane Domain (Token + Rewards)

- `src/jane/Jane.sol` implements the JANE token with role-based mint/transfer controls and `MarkdownController` integration for borrower freezes and redistribution.
- `src/jane/RewardsDistributor.sol` implements cumulative merkle-based rewards claims, optional mint-vs-transfer payout mode, and global emissions caps.
- `src/MarkdownController.sol` orchestrates markdown-driven borrower freezing and proportional/full redistribution calls into `Jane`.
- Security boundaries center on:
  - role ownership and minter finalization in `Jane`
  - owner-only root/emission updates in `RewardsDistributor`
  - `onlyMorphoCredit` and markdown enablement gates in `MarkdownController`

## LCC Domain

- `src/lcc/LCCVault.sol`: per-facility callable-credit vault (not ERC-4626, no transferable shares). One ERC20 `marginAsset` is posted as a performance bond, valued through a trusted Morpho-style `IOracle`, and leveraged by `marginRatioBps` into a callable commitment denominated in the vault's `fundingAsset`. The spec term "callable asset" maps to `fundingAsset` in code because that token funds calls and auction fills.
- Topology: `LCCAuctionLib`, `LCCConfigLib`, and `LCCExitLib` are the three externally linked libraries in the shared `LCCVault` implementation. An `UpgradeableBeacon` owned by 3Jane's existing 7-day timelock points at that implementation, and `src/lcc/LCCVaultFactory.sol` deploys per-facility `BeaconProxy` instances with atomic initializer calldata. The implementation constructor fixes protocol-wide `notificationVault`, `usd3`, `fundingAsset`, and `treasury`; per-facility params live in proxy storage.
- Build constraint: the canonical Forge `LCCVault` artifact is compiled for Cancun with official solc `0.8.35`, via IR, and 150 optimizer runs. The measured runtime is 24,144 bytes, 132 bytes below the internal ceiling and 432 bytes below EIP-170; `yarn build:forge:size` enforces the compiler settings, 24,276-byte internal ceiling, and three-linked-library topology. The active-only monolith measured 24,703 bytes, 127 bytes over EIP-170, so exit exposure and maturity assignment remain extracted into `LCCExitLib`. `ReentrancyGuardTransient` makes EIP-1153 support mandatory. Hardhat uses pinned stable solc-js `0.8.35` for compile/test-only Cancun output, while non-LCC production artifacts remain Shanghai.
- Bouncer scope: `bounceCommitment(user, commitment)` removes only active commitment and returns its pro-rata active margin. Pending deposits must first fold, and an exit in progress is left to its normal claim path. Removing an otherwise plain account's entire active commitment leaves zero exposure, allowing the family registry to repoint lazily on the user's next deposit. As a trusted instant-exit valve, bounce bypasses `exitDelayEpochs`, `exitCapBps` bucket capacity, and `minCommitmentEpochs`. Full closeout is deferred in `docs/lcc-deferred-full-closeout-bounce.md`.
- `src/lcc/LCCVaultFactory.sol`: the non-upgradeable family authority, admission registry, and owner-gated `BeaconProxy` deployer. A deliberately unheld `DEFAULT_ADMIN_ROLE` makes two-step ownership transfer the sole mutation path for the single `OWNER_ROLE`; that role administers `LISTER_ROLE`, `BOUNCER_ROLE`, and family-wide `GUARDIAN_ROLE`, and cannot be renounced. Deposits are whitelisted and prospectively limited to one open family vault by default, with independent owner kill switches; the optional admissions module contributes only a static decision on first deposits, closed-account reopens, and cross-pointer admissions, while top-ups in the currently registered open vault bypass it and the factory performs every registry write. The beacon is public, but non-factory proxies cannot pass the deposit gate and EOA initialization is rejected.
- Registry migration is lazy: the last authorized vault is stored in `vaultOf`, and a deposit into another family vault may repoint it only when bounded account replay of that named vault completes with zero exposure. Incomplete replay is conservatively open, and matured exits remain open until claimed. The admission path never scans the unbounded family list. Disabling one-vault enforcement keeps last-deposit recording warm but makes no exclusivity claim; re-enabling is prospective, so positions opened during the disabled interval are not retroactively closed. Deliberate owner-accepted residual: a user who opened A then B while the policy was off can leave A open while `vaultOf` names B; after re-enabling, closing and reopening B passes the named-vault check and restores two open positions. This is bounded to users grandfathered by a policy-off window, is unreachable for a user whose entire history is under an enabled policy, and is accepted as the same prospective-only carve-out instead of imposing an unbounded scan of bounded-replay calls on every deposit. Operators must reconcile multi-vault users offchain before re-enabling the policy.
- Lifecycle: epochs and phases (`Normal`, `PreCall`, `Funding`, `Closed`) are derived from a pause-adjusted effective clock. The factory owner opens at most one call per epoch during `PreCall`; users fund all-or-nothing pro-rata obligations during `Funding`; unfunded accounts are slashed after the deadline. `maxEpochs` optionally schedules a terminal withdraw-only phase after a finite number of callable cycles (`0` means perpetual). Any factory guardian or the factory owner can pause synced entrypoints and freeze the derived clock; unpause is owner-only with no time bound and resumes every window exactly where it froze. Shutdown ends an active pause without advancing effective time so wind-down claims become immediately available while funding-window slash semantics remain frozen at the pause instant. Pausing remains available after shutdown as a circuit breaker for the claim path.
- Amount-like accounting values outside the margin family are denominated in `fundingAsset` unless explicitly documented otherwise. Margin values are denominated in `marginAsset`; `marginValue` is margin valued in the funding asset before leverage.
- Slashed margin backs an epoch-shortfall auction during the `Closed` phase (or follows the same surplus-disposal path when the auction is disabled, there is no shortfall, or finalization happens after the window): fillers' funding asset fills the remaining call shortfall and is delivered as wrapped USD3l, plus a collateral kicker that steps up over the window — the award curve reserves the configured treasury take, with the window divided into `auctionStepCount` steps and per-fill awards capped by `maxAuctionAwardBps` at the live fill-time oracle price (`src/lcc/libraries/LCCAuctionLib.sol`, externally linked). Completed settlement charges `slashFeeBps` on the greater of cumulative awards and cumulative fills' pro-rata first-step offer, and diverts the gross pool's unfilled share to treasury; an eligible zero-fill epoch therefore sends its whole pool to treasury even if lazy finalization never opened an auction record. A shutdown strictly before the Closed end, zero shortfall, or disabled auction remains ineligible and returns the unawarded pool without a take. The remaining return pool is converted to commitment at the validated price frozen at call open, so the conversion price is frozen but the amount converted is not. Residual shortfall does not roll over.
- No keeper: all state progression is lazy. A `synced` modifier folds due pending activations, exit maturities, and eligible slash finalizations on every touch; per-user state is materialized by replaying finalized calls through a bounded cursor (`materializeAccount` is permissionless).
- Funding routes the funding asset through USD3 into the USD3 Notification Vault (`USD3l`) for the funder. Self-funders choose per call whether to amortize (`fundCall(false)`, releasing proportional margin and reducing commitment) or roll (`fundCall(true)`, paying the obligation while retaining full margin and callable commitment). Rolled exposure re-arms every epoch, so repeated rolling keeps the account's full commitment callable and can make later pro-rata obligations larger as amortizers decay. Third parties may fund a user's obligation push-style via `fundCall(address)` (the caller pays; all proceeds accrue to the user), and push funding always amortizes so the payer cannot keep the user's margin locked. Funding pulls `max(obligationAmount, usd3.previewMint(1))` so every successful delivery mints at least one USD3 share, with at most 1,000 extra funding-asset base units; settlement remains obligation-denominated. `previewMint(1) == 0` reports an undeliverable zero-asset/nonzero-supply USD3 state: pause to freeze the deadline, then owner-shutdown before the frozen deadline. Other USD3 or notification-vault failures revert atomically and can be retried while the window remains open.
- Heavy rolling keeps `protocolCommitmentCap` utilization pinned because rolled accounts do not decrement active commitment, reducing deposit headroom. Auction-eligible going-concern surplus disposal uses a call-local funded base that conservatively treats every funded account's call-open commitment as surviving; a current cap at or below that base zeroes the paired return pool, while a positive commitment clamp preserves the full recovered margin. Auction-ineligible disposal, shutdown-truncated disposal, and disposal of the last callable epoch (or later) bypass the protocol-cap clamp. Eligibility describes auction opportunity while the clamp protects future-call capacity. A kicked epoch can become ineligible when shutdown lands mid-window, but `shutdownTruncated` implies `windDown`, so the clamp condition already excludes it. Deposits cannot influence either bound; owners manage the current cap with `setRiskCaps`, whose live-slot guard freezes both raises and reductions. Per-account replay credits each defaulter its full floored pro-rata share of both the return pool and the returned commitment with no per-user cap bound (deliberately reopened M-01): post-credit exposure can exceed the live `userCommitmentCap`, which gates deposit admission only, and the headroom clamp caps each cycle's returned commitment at the commitment the slash removed, so repeated default/return cycles cannot grow aggregate exposure (a rising call-open price pins the return at the slashed commitment; a falling price marks it down and the clamp prevents marking it back up) — an account can still exceed its own slashed commitment, with no per-user ceiling, by absorbing co-defaulters' margin-keyed pro-rata share of the epoch's return.
- Exits are full-account, irrevocable, and assigned first-fit to per-epoch maturity buckets with capacity `max(1, max(protocolCommitmentCap, activeCommitment) * exitCapBps / BPS)`; exiting accounts remain liable until maturity. `requestExit(maxDeferralEpochs, deadline)` lets the caller bound both assignment and wall-clock freshness: `exitDelayEpochs` is the delay from now to the earliest available maturity (`currentEpoch + exitDelayEpochs`), while deferral starts there; 0 accepts only that maturity, `N` accepts up to `N` later epochs, and `type(uint256).max` accepts any. This deferral is unrelated to the `maxEpochs` sunset schedule. Capacity is recomputed per request from aggregate `activeCommitment`, deliberately introducing path dependence: it can decline as active commitment declines through amortization or slashing, but never below the configured-cap value at that request. Any unattributed return-credit residual in the aggregate (pair-drop orphans, which scale past flooring dust when the conversion pins at `MIN_RETURN_COMMITMENT`) only widens capacity. Pending-activation and exit-maturity margin/commitment pairs each occupy one packed `LCCTypesLib.Bucket` word, while the four original `uint256` field getters preserve the external ABI. Per-call exit exposure packs six `uint128` amounts into three words and retains an explicit `listed` word so maturity-list membership remains exact-once; the linked `LCCExitLib` performs assignment, snapshots, funding reconciliation, and slash reduction against those unchanged storage roots. Auction state similarly packs its four `uint128` counters into two words; `getAuctionState` keeps the same wire encoding, and the linked `LCCAuctionLib` records packed fills. A vault may set `minCommitmentEpochs` (immutable, up to 64, 0 disables): `requestExit` reverts `CommitmentNotMature` until that many epochs have passed since `commitmentStartEpoch`, the later of the account's latest deposit activation epoch and one epoch after the call that produced its latest nonzero return-pool re-credit. The latter is the deterministic first epoch in which the credit can back a new call, so lazy disposal delay cannot extend the gate. Every deposit and any such nonzero credit advances the clock monotonically, rounding-dropped credits and funding of any kind never touch it, and the wind-down claim bypasses the gate. Live maturity buckets are hard-capped at 128 (`requestExit` reverts `ExitCapacityReached` when a new bucket would exceed it). The configuration bounds `exitDelayEpochs <= 64` and `exitCapBps >= 313` keep worst-case honest exit demand, including first-fit fragmentation, within that cap. Scan termination relies separately on the runtime clamp: capacity is at least one, so any empty bucket terminates the scan and only nonzero-commitment buckets are skipped; `LCCExitLib` keeps those buckets in the maturity list, which is capped at 128, so the scan takes at most 129 iterations. The limit remains reachable through cap-raise sequences whose exact-capacity deposits each open a new maturity. `claimExitedMargin` handles normal matured exits, while `claimRemainingMargin` withdraws remaining active, pending, or matured-exit margin after shutdown or terminal sunset. A lagging account more than 64 finalized calls behind may need permissionless `materializeAccount` batches before the wind-down claim succeeds.
- Trust model: the factory owner and margin oracle are fully trusted. One two-step factory ownership rotation re-keys every vault; owner-role renunciation is blocked, and the unheld default admin prevents minting additional owners. `isOwner`, `isGuardian`, and `requireBouncer` are non-upgradeable, local role-storage views and must never route through an admissions module or other external call. The margin oracle is owner-rotatable through `setMarginOracle`; rotation reprices subsequent deposits and fill awards but not the price used to convert an opened call's remaining return pool. During a pause the owner may replace even a responsive oracle because fills cannot execute; while unpaused, a responsive oracle still blocks mid-auction rotation and the existing zero-price/reverting-oracle recovery carve-out remains. Call open rejects a zero or reverting oracle and freezes the nonzero price outside the ABI-returned `EpochState` but exposes it in `EpochCallOpened`. A missing snapshot is therefore corruption/future-writer recovery: only an owner-triggered sync may consult the live oracle. Price-failure tolerance follows actual shutdown or terminal state, while the protocol-cap exemption remains anchored to a shutdown before that epoch's Closed end or to the last callable epoch (or later). This split keeps shutdown and terminal claims non-bricking without making valid-price allocations depend on settlement time. If the snapshot and live oracle are both dead, the owner must rotate the oracle before the recovering `synced` call; shutdown alone safely sweeps rather than recovers the pool. Do not rotate factory ownership while any family vault has a pending auction slot with a missing price snapshot: oracle rotation and the owner-triggered recovery sync must stay under one owner. Factory guardians can only pause, while shutdown and oracle rotation remain live during a pause for incident response. The margin asset must be a standard ERC20 (no fee-on-transfer/rebasing). The beacon owner can replace logic under every beacon-backed LCC vault; this fleet-upgrade authority is mitigated by the 7-day timelock delay.
- Operational requirement: each LCC vault must be added to USD3's `supplyCapExempt` list so funding and auction-fill deposits bypass supply-cap headroom and first-time minimum deposits. A zero USD3 supply cap remains an emergency pause and blocks even exempt vaults.
- Upgrade safety checklist: the v2 fresh-family layout has no persistent reentrancy slot, starts with `_clockConfig` at slot 0, stores the captured `factory` at slot 29, and retains a 49-slot `__gap` beginning at slot 30. There is deliberately no `factory()` getter within the tight runtime budget; integrators verify provenance through the exact inverse registry check `factory.isVault(vault)`, never by reading slot 29. After deployment, never reorder storage variables or base contracts; append new state by consuming `__gap`; treat the packed structs in `LCCTypesLib` and the `isAccountClosed` predicate as upgrade-frozen; keep `_disableInitializers()` in implementation constructors; re-link `LCCAuctionLib`, `LCCConfigLib`, and `LCCExitLib` whenever a new implementation is deployed. `LCCExitLib` anchors at `exitBucketByMaturity` and relies on the next four exit-storage roots remaining consecutive, so their adjacency is also upgrade-frozen. `factory` is written once in `initialize`, is the sole authority source and a frozen settlement input, and must never gain a setter. `initialize` must never call an `isVault`-gated factory function because proxy registration occurs after construction. `finalizedCallPrefix` must advance in the same transaction as `slashFinalized`, preserving bounded replay's closure guarantee. Every future implementation must preserve the property that runtime exit capacity is at least one, or normalize existing configurations during the upgrade. Every implementation that sets `callOpened` to true must write a validated nonzero `marginPriceAtCallOpen` for that epoch in the same transaction; otherwise a missing price blocks non-owner going-concern disposal. Return-pool replay credits each defaulter its full paired share with no per-user cap bound (a deliberate reopening of audit finding M-01), keeping global totals equal to the sum of per-account commitments up to the pair-drop residual (flooring dust per epoch, except when the conversion pins at `MIN_RETURN_COMMITMENT`, where it scales with the dropped margin); any future implementation reintroducing a per-account bound on that credit must restore a sweep for the resulting unattributable commitment. Every settlement input is frozen for the disposed epoch or read only from a setter protected by `synced` and, for the sole auction-slot deferral channel, a live-slot guard; the `setRiskCaps` protocol-cap guard covers raises and reductions. Any new settlement input must be classified the same way before merge. Caller-side auction bounds make fills more likely to revert, so auctions stay live longer in expectation. That is safe only because commit `1e4a2761` first removed the live-auction replay barrier and the earlier price-snapshot work froze return-pool valuation at call open, so shifting settlement from mid-window to window-end cannot change the disposal price. Any future implementation that reintroduces a global replay barrier on live auctions, or unfreezes disposal valuation, must revisit these bounds. `yarn build:forge:size` reads the storage layout embedded in the canonical build-profile artifact and recursively canonicalizes encoding, widths, mappings, arrays, and packed struct members before comparing it with the versioned, reviewer-controlled `docs/lcc-vault-storage-layout.json`; the gate never regenerates its baseline.
- Deferred (policy, not physics): the EpochState/RiskConfig storage repack — measured record in `docs/lcc-deferred-epochstate-repack.md`.

## Current Invariant Execution Model

- Core invariants run fast/deep profiles in CI.
- USD3 invariants are currently expected to expose one known failing invariant and are gate-checked for exactly that failure signature.
- This expected-failure gate must be removed once underlying protocol behavior is fixed.
